# Sessions separate creation, replay, reattachment, and disposal

Stable v1 starts with `session/new { cwd, mcpServers }`; the agent returns a unique `sessionId`. The absolute working directory anchors the conversation, while each MCP entry tells the agent which external server to connect to ([session setup, L9–L17](https://agentclientprotocol.com/protocol/v1/session-setup)).

Persistence has two distinct operations. Capability-gated `session/load { sessionId, cwd, mcpServers }` must replay the **entire** history as `session/update` notifications before its response ([session setup, L19–L50](https://agentclientprotocol.com/protocol/v1/session-setup)). Stabilized `session/resume` is separately gated by `sessionCapabilities.resume`; it reconnects MCP servers and restores context **without** replay ([session setup, L51–L76](https://agentclientprotocol.com/protocol/v1/session-setup)).

`session/list` requires `sessionCapabilities.list`; optional `cwd` filters by absolute working directory, `cursor` paginates, and the result contains `sessions: SessionInfo[]` plus optional `nextCursor`. Listing only discovers sessions—it does not activate one ([session list, L24–L63 and L93–L99](https://agentclientprotocol.com/protocol/v1/session-list)). `session/delete { sessionId }`, gated by `sessionCapabilities.delete`, removes an entry from later lists; nonexistent IDs should succeed, while storage policy and deletion of active sessions remain implementation-defined ([session delete, L6–L30](https://agentclientprotocol.com/protocol/v1/session-delete)).

Two former RFDs are now in stable v1: `session/resume` and `session/close`. The latter, gated by `sessionCapabilities.close`, cancels work and frees active-session resources ([session setup, L78–L106](https://agentclientprotocol.com/protocol/v1/session-setup)). `session/fork` remains an RFD proposal rather than stable v1: consumers must not assume it exists merely because the agent supports sessions ([session fork RFD](https://agentclientprotocol.com/rfds/session-fork)).
